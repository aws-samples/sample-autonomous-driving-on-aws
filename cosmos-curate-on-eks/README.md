# NVIDIA Cosmos Curate on Amazon EKS (CPU only)

Run the [NVIDIA Cosmos Curate](https://github.com/nvidia-cosmos/cosmos-curate) video curation
pipeline on Amazon EKS **without GPU instances**. Scene splitting, filtering, and embeddings run on
CPU nodes; captions are generated by Claude on Amazon Bedrock through a small OpenAI-compatible proxy.
Embeddings are indexed in Amazon OpenSearch Serverless for text and vector search.

[한국어](README.ko.md)

## Architecture

```
                         Amazon EKS (private subnets, 4 x 16-vCPU nodes)
 ┌───────────────────────────────────────────────────────────────────────────────┐
 │  Cosmos Curator StatefulSet (upstream Helm chart, one Ray node per pod)        │
 │    pod-0 = Ray head          pod-1..3 = Ray workers                            │
 │    split (TransNetV2) -> filters -> Cosmos-Embed1 embeddings -> captions ──┐   │
 │                                                                             │   │
 │  caption-proxy (Deployment, 2 replicas) <── OpenAI-compatible requests ────┘   │
 └────────────┬────────────────────────────┬────────────────────────────┬────────┘
              │ Converse API (frames)      │ model weights, videos,     │ embeddings
              ▼                            ▼ clips, metadata            ▼
       Amazon Bedrock (Claude)        Amazon S3                  OpenSearch Serverless
```

- **Curator** runs the upstream chart with a CPU image built from `docker/Dockerfile.cpu`.
  `docker/patch_cpu.py` patches three places that assume CUDA (TransNetV2, Cosmos-Embed1,
  and the embedding stage's CPU request) and fails the build if upstream code changed.
- **Caption proxy** (`docker/caption-proxy/`) receives Curator's OpenAI-style caption requests,
  extracts 8 evenly spaced frames from each caption window with ffmpeg, and calls the Bedrock
  Converse API (the Claude model does not take video input).
- **Model weights** are downloaded once from Hugging Face into S3 (`bootstrap/seed_models.sh`,
  sha256-checked) and synced to every node at job start. No weights are stored in this repository.
- **Access**: EKS Pod Identity gives the pods S3, Bedrock, and OpenSearch access. No keys are stored.

### Node options

All options use four 16-vCPU x86 nodes (8 interchangeable instance types such as c7i/m7i/c6a.4xlarge)
and four Curator pods, one per node.

| `OPTION` | Nodes | Ray head | Use |
|---|---|---|---|
| `a` | 4 on-demand | on-demand | Jobs that must not be interrupted |
| `b` (default) | 3 Spot + 1 on-demand | on-demand | Balance of cost and stability |
| `c` | 4 Spot | Spot | Lowest cost; a reclaimed head node stops the job |

Losing any Ray node fails the running Curate job. `k8s/run_split.sh` detects a job that failed because
a node died, waits until the Ray cluster is whole again, and resubmits it into a new output prefix
(up to 3 attempts); the job restarts from the beginning. Losing the head also loses the job's state.
Option `b` keeps the head off Spot: the on-demand node is tainted `dedicated=curator:NoSchedule` so
only Curator pods can use it, and the StatefulSet is switched to `OrderedReady`
(`k8s/post-renderer.sh`) so pod-0 is created first and takes that node. `setup_curator_pod.sh`
verifies that pod-0 is on the on-demand node.

If Spot capacity or quota is unavailable, `deploy_new_region.sh` detects the node launch errors and
redeploys with option `a`.

## Prerequisites

- AWS account and credentials allowed to create VPC, EKS, IAM, S3, ECR, OpenSearch Serverless, and
  CloudFormation resources, and to invoke Claude on Amazon Bedrock
  (inference profile `global.anthropic.claude-opus-5-5`)
- 64 vCPU of EC2 quota in the target region (48 Spot + 16 on-demand for option `b`, 64 on-demand for `a`)
- A **Linux** build host with Docker and at least **40 GB free Docker disk** (the CPU image is about
  30 GB; a 100 GB root volume is recommended), AWS CLI v2, kubectl, Helm 3, Node.js 20+, git, openssl
- The image build downloads PaddlePaddle wheels from a server in China; in our tests this timed out
  from US build hosts and worked from Asia Pacific (Seoul)

## Quick start

```bash
git clone https://github.com/aws-samples/sample-autonomous-driving-on-aws.git
cd sample-autonomous-driving-on-aws/cosmos-curate-on-eks

# Empty region -> infrastructure, images, model weights -> Ray cluster ->
# split + Cosmos-Embed1 + Bedrock captions -> OpenSearch -> text and kNN search check
scripts/e2e.sh us-west-2                    # uses the 30 s sample video bundled in the image
scripts/e2e.sh us-west-2 ./my-videos        # or your own .mp4 files
OPTION=a scripts/e2e.sh us-west-2           # choose a node option (default b)

# Remove everything, including the retained S3 bucket (and its data) and ECR repositories
scripts/teardown.sh us-west-2
```

`e2e.sh` can be re-run; finished steps are skipped. A full run from an empty region takes about
65-100 minutes, mostly the image build and push, EKS creation, and each node pulling the 14.5 GB image.

### What the steps do

| Script | Does |
|---|---|
| `scripts/deploy_new_region.sh <region>` | CDK bootstrap; `CosmosCurateCore` (VPC with 1 NAT gateway, S3 bucket `cosmos-curate-<account>-<region>`, ECR repositories `cosmos-curate/curator-cpu` and `cosmos-curate/caption-proxy`); image build and push; model weights to S3; `CosmosCurateEks` (cluster, node groups, Pod Identity); `CosmosCurateOpenSearch` |
| `scripts/build_and_push_images.sh <region>` | Builds both images; reuses a local image with the same build context for another region |
| `scripts/setup_curator_pod.sh <region> [replicas]` | Curator config (ConfigMap), caption proxy, Curator Helm release, head placement check, waits until all Ray nodes have joined |
| `k8s/run_split.sh <region> <dataset>` | Submits split + embedding + caption as a Ray job on `s3://<bucket>/inputs/<dataset>/`; prints the output prefix |
| `scripts/upload_embeddings_to_opensearch.py` | Indexes a run's embeddings and captions (run inside pod-0, which has OpenSearch access) |
| `scripts/verify_opensearch.py` | Fails unless the run's documents are searchable with both text and kNN queries |
| `scripts/teardown.sh <region>` | Deletes the Helm release, stacks, S3 bucket, and ECR repositories |

## Running the pipeline on your videos

```bash
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
aws s3 sync ./my-videos s3://cosmos-curate-${ACCOUNT_ID}-us-west-2/inputs/my-videos/
k8s/run_split.sh us-west-2 my-videos
```

`run_split.sh` runs Curate's `split` pipeline with TransNetV2 shot detection on CPU, Cosmos-Embed1-336p
embeddings, and captions through the proxy. Outputs (clips, metadata with captions, embeddings,
`summary.json`) are written under `s3://<bucket>/outputs/<dataset>/<run-id>/`.

Two settings are required for this setup and are already in the script:

- `--runtime-env-json '{"env_vars":{"NVCF_MULTI_NODE":"false"}}'`: the Helm deployment sets
  `NVCF_MULTI_NODE=true`, which makes Curate fetch weights from NVIDIA NGC instead of `--model-weights-path`.
- `pixi run --as-is`: without `--as-is` pixi tries to update the environments in the image and fails.

Captions are generated per caption window, not per clip, so longer clips mean more Bedrock calls.
To change what the captions describe, pass a prompt with `--captioning-prompt-text`
(`k8s/prompts/caption_prompt.txt` is a general example).

To index and search a run (`<prefix>` is the path after the bucket, printed by `run_split.sh`):

```bash
export KUBECONFIG=~/.kube/cosmos-curate-us-west-2
ENDPOINT=$(aws cloudformation describe-stacks --stack-name CosmosCurateOpenSearch --region us-west-2 \
  --query "Stacks[0].Outputs[?OutputKey=='CollectionEndpoint'].OutputValue" --output text)
kubectl cp scripts/upload_embeddings_to_opensearch.py cosmos-curator/cosmos-curator-0:/tmp/upload.py
kubectl -n cosmos-curator exec cosmos-curator-0 -- bash -c "pip3 install --user --quiet opensearch-py && \
  python3 /tmp/upload.py --collection-endpoint ${ENDPOINT} --bucket cosmos-curate-${ACCOUNT_ID}-us-west-2 \
    --prefix <prefix> --region us-west-2 --index-name video-clips"
```

## Cost

Main cost drivers, to be priced with your region's current rates:

| Item | Formula |
|---|---|
| Nodes | Σ(nodes per group × hourly price) × job duration |
| Captions | caption windows × (input tokens × input price + output tokens × output price) |
| Always on while the stack exists | EKS control plane, NAT gateway (hourly + data processing), OpenSearch Serverless OCUs, S3 storage |

Captioning usually dominates when enabled. Run a small batch first and check the token usage per window.
Scaling the node groups to zero does not stop the control plane, NAT gateway, or OpenSearch charges;
run `scripts/teardown.sh` when you are done. See [Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)
and [Amazon EKS pricing](https://aws.amazon.com/eks/pricing/).

## Security

This is a sample, not a production deployment. Review these before using it with real data:

- **EKS API endpoint** is public and private. Restrict the public endpoint to your network with
  `PUBLIC_ACCESS_CIDRS=203.0.113.0/24 scripts/e2e.sh <region>` (comma-separated; the host running
  the scripts must be inside one of the CIDRs), or make it private.
- **S3**: the bucket blocks public access, is encrypted with S3-managed keys, and denies non-TLS requests.
  Server access logging, VPC flow logs, and EKS control plane logging are off to keep the sample's cost
  down; turn them on for production.
- **OpenSearch Serverless** network policy allows public access to the collection endpoint; access is
  controlled by IAM and the collection's data access policy. Use a VPC endpoint for production.
- **Bedrock data location**: the global inference profile can process requests in other regions.
  If frames must stay in one region, use a regional model/profile and update the IAM policy.
- The Curator pods and the caption proxy share the `default` service account in `cosmos-curator`
  (the upstream chart does not let you set the Curator service account), so both get the same IAM role.
- `teardown.sh` deletes the S3 bucket **including all data**; the bucket and ECR repositories are
  otherwise retained by CloudFormation.

The Curator image installs upstream Cosmos Curate v2.8.0's locked Python environment (`pixi.lock`)
unchanged. An image scan reports known vulnerabilities in some of those pinned packages (for example
pillow, PyJWT, aiohttp, transformers); scan the image and rebuild on a newer upstream release before
production use.

The CDK app runs [cdk-nag](https://github.com/cdklabs/cdk-nag) `AwsSolutionsChecks` on every synth.
Each remaining rule is suppressed in `cdk/bin/cdk.ts` with the reason (mostly resources generated by
the CDK EKS module).

See [CONTRIBUTING](../CONTRIBUTING.md#security-issue-notifications) for reporting security issues.

## Troubleshooting

| Symptom | Cause | Fix (already in the scripts) |
|---|---|---|
| Weights downloaded from NGC / `NGC_NVCF_API_KEY not found` | `NVCF_MULTI_NODE=true` from the Helm deployment | Pass `NVCF_MULTI_NODE=false` in the job runtime env |
| `Not enough CPU resources ... requires 17 CPUs but only 15` | One pod exposes 15 Ray CPUs | At least 2 Curator pods (default 4) |
| Workers fail with `InvalidAuthToken` after an upgrade | A new Ray token was generated | Reuse the `ray-auth-token` secret |
| `OpenAI caption configuration not found` | Wrong config schema | `openai.caption.{base_url,api_key}` in the ConfigMap; restart pods after changes |
| OpenSearch `403` from the pod | Missing IAM `aoss:APIAccessAll` | Granted in `eks-stack.ts` |
| `Field 'embedding' is not built for ANN search` | Index created without `index.knn` | Created with `index.knn: true` |
| kubectl `Unauthorized` after a deploy | Deploying role not in aws-auth | `deploy_new_region.sh` passes `-c kubectlRole=<role>` to every deploy |
| Embedding stage runs for an hour on some nodes | bf16 on a CPU without AMX (c5/m5/c6i/m6i, AMD c6a/m6a) is 5-300x slower than fp32 | `docker/patch_cpu.py` uses bf16 only on CPUs with AMX (c7i/m7i), fp32 otherwise |
| Job fails with `The actor died because its node has died` | A Spot node was reclaimed during the job | `run_split.sh` repairs the Ray cluster and resubmits (up to 3 attempts) |
| Node `disk-pressure`, `ImagePullBackOff` | 14.5 GB image | 120 GB node disks |
| Stack stuck in `DELETE_FAILED` | Cluster still updating during deletion | Re-run `scripts/teardown.sh` |

Useful commands (with `KUBECONFIG=~/.kube/cosmos-curate-<region>`):

```bash
kubectl -n cosmos-curator get pods -o wide
kubectl -n cosmos-curator exec cosmos-curator-0 -- pixi run --as-is ray status
kubectl -n cosmos-curator logs -l app=caption-proxy
# Ray wraps stage errors; the root cause is in the worker logs:
kubectl -n cosmos-curator exec cosmos-curator-0 -- bash -c 'tail -n 50 /tmp/ray/session_latest/logs/worker-*.err'
```

## Deploy with a coding agent

[`CLAUDE.md`](CLAUDE.md) describes how a coding agent should deploy, validate, and debug this sample.
Open the repository in a coding agent such as [Claude Code](https://claude.com/claude-code) and ask, for example,
"Deploy to us-west-2 and run the end-to-end test." The agent runs `scripts/e2e.sh` and treats the run
as passed only when the search check succeeds.

## Validation

`scripts/e2e.sh` passed from an empty region (no stacks, ECR repositories, or S3 bucket) with the
bundled sample video for every node option: `a` in us-west-2 (4 x c7i), `b` in ap-northeast-1
(c7i on-demand head, c5/m5 Spot workers), `c` in ap-southeast-1 (4 x c5 Spot). Each run produced
4 clips, 4/4 successful captions, and 4 searchable documents, and text and kNN queries returned the
clips. A further run in ap-southeast-1 (option `b`, `PUBLIC_ACCESS_CIDRS` set to the build host)
deleted a worker pod during the first job's embedding stage; `run_split.sh` repaired the cluster and the
second attempt passed. Tested with Cosmos Curate v2.8.0.

## Limitations

- Shot detection and embeddings on CPU are much slower than on GPU; measure with a small batch first.
- Caption throughput is bounded by your Bedrock quota rather than node count.
- A lost worker restarts the job from the beginning (tested by deleting a worker pod mid-job, and seen
  with a real Spot rebalance in us-west-2). Long jobs lose their progress; split large inputs into
  several datasets. Losing the head (option `c`) takes the same retry path but was not tested.
